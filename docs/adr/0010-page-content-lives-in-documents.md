# Page content lives in its own document, not in the Venue

The site has five route shapes under a Venue: its home page, a page per game, a page per event, a gift page and a booking page. Every one of them shows a Page Cover and an editor-composed array of Page Components. The `venue` document already held the home page's cover as five flat fields and the venue's games as an `offerings` array of `{ game, price }`, so the obvious move was to keep going — nest the other four pages in the same document.

That was tried on paper and rejected. **Page content is not a fact about a physical location.** A Venue is an address, a phone number, seven opening-hour strings and a logo; marketing copy for the gift page is none of those, and putting it there means the document grows a page's worth of JSON for every game the venue sells. The editing consequence is worse than the modeling one: Sanity's draft/publish granularity is the document, so publishing a finished gift page also publishes whatever half-written opening hours were sitting in the same draft. Nesting also costs the page its own URL in the Studio, its own revision history, and any hope of a Presentation preview pointed at it.

A **Venue Game** is one document per (Venue, Game Format) pair, holding the price and the page. This is the shape that makes the sentence "Lille sells Musi'Quiz" have exactly one home. The alternative kept `venue.offerings` for the price and added a second document for the page, which asserts the same fact twice and invites the two to disagree — a page for a game the venue does not sell, or a game listed with no page behind it. Merging them means the venue's game list is a query (`*[_type == "venueGame" && venue._ref == ^._id]`) rather than an array, which is why ordering moved to `displayOrder` on the Game Format: documents come back unordered, and a per-venue order would be one more thing to hand-sync across venues that want the same order anyway.

**Venue Event is a separate document type from Venue Game**, not a Venue Game with a `kind` field. The two differ in ways a discriminator has to encode as conditional fields — `price` exists only for games, and the reference points at a different type per kind — and `z.strictObject` cannot narrow on a discriminator without a union that no query needs, since every query already knows which kind it is fetching. The cost is a dozen duplicated field definitions, which is what this repo already chooses over coupling.

**Venue Page is one document type for home, gift and book**, with a `pageType` enum, and this is not a contradiction of the paragraph above. The test is whether the discriminator is shape-bearing. For games and events it is; for the three fixed pages it is not — all three are a Venue reference, a Page Cover and a Page Component array, byte for byte. The enum names which route renders the document and nothing else, so there are no conditional fields, no hidden inputs and no union in the schema.

The three Venue Pages get **deterministic ids** — `venuePage-${venueId}-${pageType}`, built from the venue's document id — created from fixed children in the Studio structure rather than by an editor pressing "+". Uniqueness stops being something to validate and becomes something unrepresentable: two gift pages for Lille would need two documents with one id. The id is composed from the document id rather than the slug because that is what the structure's child resolver is handed; reaching the slug would mean an async fetch on every venue click, to make an id that no editor reads anyway. The `venue` and `pageType` fields are filled from an initial value template the structure passes those same values to, and both are `readOnly` — they describe which document this is, and changing one would strand it under an id that no longer matches. Venue Games cannot use the trick, because the editor picks the pair that would form the id, so they keep an async `rule.custom` that counts existing documents for the same (venue, game) — the same guarantee the old `offerings` array validated, relocated.

`getRoutesForLang` keeps owning every URL, and the Page Cover's call to action carries **a label but no destination**. An authored internal URL would bypass the locale prefix that function exists to apply, so an editor writing `/lille/book` on the French site would ship a 404 that no schema could catch. No call to action leaves the site today; the day one does, that page's document grows a URL field, and only that one.

## Alternative: a generic `page` document with a `pageType` covering all five routes

One document type for every page, with `venue`, `pageType`, and conditionally-required `game` and `event` references. Rejected for the reason given above — the discriminator is shape-bearing across all five, so `game` is required-if-type-is-game, which is a rule the schema states in a validation callback, the Studio states in a `hidden` callback, and Zod cannot state at all without a discriminated union per query.

## Alternative: keep offerings nested and widen the modal

`ArrayOptions.modal` accepts `{ type: 'dialog', width: 1…5 | 'auto' }`, which turns the cramped popover an offering edits in today into a wide centered dialog. It is a real fix and it is kept in reserve for small array objects elsewhere. It was not enough here: it addresses the size of the editing surface and none of the reasons above — draft granularity, document size, revision history, preview — and a Page Component array inside a dialog opens a modal on top of a modal.

## Consequences

- **A composed document id must not contain a dot.** A dot splits an id into path segments, and the grant that makes a public dataset readable without a token covers `path("*")` — single-segment ids only. This is the same mechanism that keeps `drafts.foo` private, so a dotted id is fully visible in the Studio and to any tokened client while being invisible to the site, which fetches anonymously. The failure looks exactly like a missing document. Ids composed here use hyphens, and any future scheme must too.
- **A Venue with a missing Venue Page fails the build.** The three fixed routes are emitted for every Venue, so `z.strictObject` throws at build time when the document is absent, rather than the route quietly not existing. This is deliberate: a 404 on `/lille/offrir` is discovered by a visitor, a red build is discovered by whoever caused it. It also means an editor can break a deploy, which the Studio structure mitigates by showing all three pages under every Venue whether or not they have been written.
- **Game and event routes are document-derived and cannot fail this way.** `/lille/jeux/musi-quiz` exists if and only if that Venue Game exists, because there is no rule saying every venue must sell every game.
- **`venueHomepage.ts` is absorbed by a single `venuePage.ts` Query Module** taking `pageType` alongside `lang` and `venueSlug`. Home, gift and book share one projection and one schema exactly, so they are one fetch by ADR 0009's own test — a module is its contract, and `pageType` is a closed union interpolated under the compiler's eye like `lang` already is. Three files differing by one string literal is not the duplication that ADR defends.
- **`venueFooter.ts` and `header.ts` stop reading `venue.offerings[]`** and gain a subquery over `venueGame` ordered by `game->displayOrder`. Their duplication of that projection stays duplicated.
- **Two `*Slugs` modules are added rather than one.** `venueGameSlugs` and `venueEventSlugs` back two different route files' `getStaticPaths`, and one module serving both would return a payload each caller half-ignores.
- **Routes gain collection segments and stay localized.** `/[venue]/jeux/[game]` and `/[venue]/evenements/[event]` in French, `/games/` and `/events/` in English. `getRoutesForLang`'s current `venueGame` returns `/${venue}/${game}`, putting game slugs in the same namespace as `reserver` and `offrir`, where a game slugged "offrir" shadows the gift page and Astro's route priority silently picks a winner. Slugs themselves are not localized: one `slug` on the Format, the same segment in both locales, as Venue slugs already work.
- **The migration is 13 documents of existing data and 10 pages of writing.** Five venues, two game formats, eight published offerings. The gift and booking pages have no content to migrate because they have never existed — under the build-failure rule above, writing them is what unblocks the deploy, and that is a content task on the critical path, not a code one.
- **Old fields are deleted in the same change that adds the new types.** No deprecation window, because the site has not shipped and the dataset is small enough to re-enter by hand.
